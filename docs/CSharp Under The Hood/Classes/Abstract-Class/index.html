Abstract Classes (Klasy abstrakcyjne)

Definition​

  • Declared using the abstract keyword (public abstract class).
  • An abstract class acts as a foundational, unfinished archetype. It can contain:
    • Abstract methods (signatures with no implementation {}; derived classes are forced to override and implement them).
    • Regular / virtual methods (fully implemented behaviors that derived classes inherit out-of-the-box).
    • Properties, fields, and constructors (used to initialize shared state when a derived class is spawned).
  • Crucial rule: You cannot instantiate an abstract class directly (new is strictly forbidden by the compiler). It exists solely to be inherited from.
The Metaphor: Dramatic Archetypes

An abstract class is like the literary concept of a "Phantom" (Osoba Dramatu) in Wyspiański’s script:

  • A "generic, nameless Phantom" never walks onto the stage in Bronowice—you cannot summon pure abstraction (new Phantom() makes no sense).
  • However, specific phantoms like Wernyhora, Stańczyk, or the Black Knight are concrete manifestations built upon that exact archetype. They all share the same ghostly nature (fading into the mist), yet each brings a completely unique historical message that they must deliver.
Design Pattern Alert: The Template Method Pattern

Abstract classes are the backbone of the Template Method Pattern. You can write a public, concrete method in the abstract class (e.g., HauntGuest()) that defines the strict skeleton of an algorithm (1. Appear from the mist -> 2. Confront the guest -> 3. Vanish), while leaving step #2 (Confront()) as an abstract method. The base class controls the overarching theatrical flow, while the subclasses fill in the specific dramatic dialogue!

public abstract class Phantom
{
    public string Name { get; set; }
    public string TargetGuest { get; set; }

    // Abstract method – NO body! Every specific phantom MUST define its own message.
    public abstract void DeliverMessage();

    // Regular concrete method – shared across all phantoms without changes.
    public void FadeIntoMist()
    {
        Console.WriteLine($"{Name} dissolves back into the cold Bronowice night.");
    }

    // Template Method Pattern in action:
    public void Haunt()
    {
        Console.WriteLine($"--- Midnight strikes for {TargetGuest} ---");
        DeliverMessage(); // Calls the overridden abstract method!
        FadeIntoMist();   // Calls the shared base method!
    }
}

public class Stanczyk : Phantom
{
    // We are forced by the compiler to use 'override' and provide the implementation
    public override void DeliverMessage()
    {
        Console.WriteLine($"{Name} hands {TargetGuest} the Caduceus to stir the muddy national waters.");
    }
}

public class Hetman : Phantom
{
    public override void DeliverMessage()
    {
        Console.WriteLine($"{Name} screams at {TargetGuest} as golden coins burn his traitorous hands!");
    }
}

Usage in the Play

class Program
{
    static void Main(string[] args)
    {
        // Phantom p = new Phantom(); // COMPILER ERROR! Cannot create an instance of the abstract type 'Phantom'.

        Stanczyk jester = new Stanczyk { Name = "Stańczyk", TargetGuest = "Dziennikarz" };
        Hetman traitor = new Hetman { Name = "Hetman Branicki", TargetGuest = "Pan Młody" };

        jester.Haunt();
        // Output:
        // --- Midnight strikes for Dziennikarz ---
        // Stańczyk hands Dziennikarz the Caduceus to stir the muddy national waters.
        // Stańczyk dissolves back into the cold Bronowice night.

        traitor.Haunt();
        // Output:
        // --- Midnight strikes for Pan Młody ---
        // Hetman Branicki screams at Pan Młody as golden coins burn his traitorous hands!
        // Hetman Branicki dissolves back into the cold Bronowice night.
    }
}

When to use Abstract Classes?

Use an abstract class when:

  • You want to avoid code duplication (DRY): Several classes share common state (Name, TargetGuest) and concrete behaviors (FadeIntoMist()) that you want to write once and inherit everywhere.
  • You need a partially built foundation: You want to provide ready-to-use base methods while strictly enforcing that every subclass implements missing critical pieces (DeliverMessage()).
  • You want to enforce a strict ontology ("Is-A" hierarchy): Since C# supports single inheritance only (a class can inherit from only one base class), an abstract class locks the derived classes into a single, closely related family tree.

Knowledge Check: Abstract Classes

  1. The Instantiation Rule: Why does the C# compiler throw an error if you try to write Phantom p = new Phantom();, and how can you still use a Phantom reference variable in your code (e.g., Phantom p = new Stanczyk();)?
  2. virtual vs. abstract: Both virtual and abstract methods are meant to be overridden in derived classes using the override keyword. What are the two critical differences between them regarding their method body in the base class and the compiler's requirement for the child class?
  3. Constructor Paradox: If you cannot instantiate an abstract class with the new keyword, why is it still legal (and very common) to write a constructor inside an abstract class? Who actually calls it?
