# Serwisy w MVVM
Kontynuacja lekcji poprzedniej.

Nasz kod możemy zmienić na bardziej `MVVM-owy`.
Utworzymy pierwszy `service`:
- dodajmy do projektu nowy folder `Services`
- umieścimy w nim pliki:
  - `IWindowService.cs`
  - `WindowService.cs`

## Czym jest Serwis (Service)?

:::note Serwis
- To **bezstanowy** (lub lekkostanowy) obiekt, który wykonuje zadania wykraczające poza kompetencje ViewModelu.
- ViewModel **deleguje** zadanie, a Serwis je **realizuje**.
- Jest realizacją zasady **DRY** (*Don't Repeat Yourself*) – jeden serwis może obsługiwać wiele ViewModeli.
:::

### Definicja techniczna

W architekturze MVVM, Serwis to warstwa pośrednicząca między **ViewModel**, a **źródłem danych** (np. API Supabase, system plików, baza danych) lub **funkcjami systemowymi** (np. wysyłanie e-maila, logowanie zdarzeń). Serwisy są zazwyczaj wstrzykiwane do ViewModeli przez konstruktor (tzw. *Dependency Injection*).



### Analogia: Architekt i Wykonawcy

Wyobraź sobie budowę domu:
* **ViewModel to Architekt:** On wie, co ma być zrobione. Ma plan (logikę UI) i wie, gdzie postawić ścianę, a gdzie okno. Ale architekt sam nie kładzie kabli ani nie montuje rur.
* **Serwis to Fachowiec (Elektryk, Hydraulik):** Architekt dzwoni do **Serwisu Elektrycznego** i mówi: „Potrzebuję prądu w tym pokoju”.
  * Architekta nie obchodzi, jakich narzędzi użyje elektryk.
  * Architekt po prostu oczekuje, że prąd będzie działał.
  * Ten sam Elektryk (Serwis) może pojechać na dziesięć różnych budów (różnych ViewModeli) i wszędzie wykona tę samą specjalistyczną robotę.

:::tip Metafora `service`
- to narzędzie zewnętrzne, które `ViewModel` tylko wykorzystuje
- Tak jak:
  - drukarka (`Service`) drukuje,
  - a Word (`ViewModel`) tylko mówi: „wydrukuj ten dokument”

:::

## Implementacja `service`

`IWindowService.cs`
```cs
public interface IWindowService
{
    void CloseWindow(object viewModel);
}
```

Przenosimy metodę zamykania okna do naszego serwisu:
:::important UWAGA!
- fragment poniższego kodu: `(w => w.DataContext == this)?`
- zamieniamy na `(w => w.DataContext == viewModel)?`
:::

`WindowService.cs`
```cs
public class WindowService : IWindowService
{
    public void CloseWindow(object viewModel)
    {
        if (App.Current?.ApplicationLifetime is not IClassicDesktopStyleApplicationLifetime desktop) return;
        desktop.Windows.FirstOrDefault(w => w.DataContext == viewModel)?.Close();
    }
}

```

**Mała zmiana**:
- klasa `App` dziedziczy po klasie `Application`
- statyczna właściwość `Current` pochodzi z klasy `Application`
- dlatego dla spójności projektu lepiej jest
    - zamiast `if (App.Current?.ApplicationLifetime ...`
    - napisać `if (Application.Current?.ApplicationLifetime ...`

:::tip Analogia: Stanowisko kontra Konkretna osoba
Wyobraź sobie, że pracujesz w dużej firmie (Twoja aplikacja):

* **Application:** To ogólne pojęcie "Dyrektora" (klasa bazowa). Każda firma ma dyrektora i każdy wie, jakie ma on uprawnienia (np. `ApplicationLifetime`).
* **App:** To konkretny dyrektor, np. "Dyrektor Jan Kowalski".

Kiedy chcesz wydać polecenie służbowe (użyć `Current`), możesz powiedzieć: *"Zgodnie z decyzją Dyrektora Jana Kowalskiego"* (`App.Current`). Jednak w oficjalnych dokumentach (Twój kod) lepiej napisać: *"Zgodnie z decyzją **Dyrektora**"* (`Application.Current`).

Dlaczego? Bo funkcja "Dyrektora" jest uniwersalna. Jeśli kiedyś zmienisz nazwę swojej klasy z `App` na `CoolGameApp`, musiałbyś poprawiać kod wszędzie. Odwołanie do `Application.Current` będzie działać zawsze, niezależnie od tego, jak nazwiesz swoją podklasę.

:::

## Wzorce projektowe
Dlaczego użyliśmy interfejsu `IWindowService` jako typu naszego `service` a nie od razu `WindowService`?
Nasza implementacja spełnia kilka wzorców projektowych:
- *Dependency Injection Principle*
    - jej praktyczne wykonanie *Program to an interface, not an implementation*
- *Service Locator*

:::note Dependency Injection Principle

Moduły wysokiego poziomu nie powinny zależeć od modułów niskiego poziomu.
Oba powinny zależeć od abstrakcji (interfejsów).

Co to znaczy u nas?
- `ViewModel` to moduł wysokiego poziomu (logika aplikacji)
- `WindowService` to moduł niskiego poziomu (konkretne API Avalonia)
- `IWindowService` to abstrakcja między nimi

ViewModel:
- zależy tylko od interfejsu
- nie zależy od `Avalonia.Window`
- nie zależy od konkretnej klasy `WindowService`

:::


:::info Program to an interface, not an implementation
- "Używaj interfejsów zamiast klas"
- "Koduj do I, nie do C"
- "Zależ od tego, co obiecuje, nie od tego, jak to robi"

:::


:::danger Service Locator
- to wzorzec projektowy, w którym istnieje centralny obiekt (tzw. lokator),
- z tego obiektu inne części aplikacji pobierają potrzebne im usługi ("serwisy").

Metaforycznie:
i -`Service Locator` to magiczna wieża gildii.
- `ViewModel` wzywa: "Potrzebuję maga od portali!"
- Wieża (`Service Locator`) wysyła odpowiedniego czarodzieja (`WindowService`).
- `ViewModel` nie trzyma maga przy sobie, tylko wzywa go, kiedy chce.


:::
